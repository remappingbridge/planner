# WEB-15 — Future release / web / README maintenance contract

**Current accepted runtime baseline:** firmware v3.2.4 release source `69a640d9767ec7198572eb9b5073ed71f8f3d202`; simulator WEB-10 accepted app files at `26aaac5c7939ddc8883aa756c6a575a3d36b808a`. WEB-15 simulator website main `905dbf86deb7fc0f7dc26601ed3714a7bb28acba` changed **only site README**, not application runtime. Current firmware docs `35b9e81ce142532d0c34da847d09079eef8ad099`. **WEB-15 acceptance is pending.**

Follow this order for future releases instead of automatically assuming a tag makes web docs current:

1. **Firmware is authoritative.** Make and validate firmware changes under its own gate/version policy, including GPIO HAT layout, 9×21 screen literals, colors, 45-screen catalog (count may change later), BLE/HID mappings, 12/30 shortcuts, and UI semantics. Test host and Pico CI and any required physical hardware flows.
2. **Publish release with integrity.** Tag release from an approved firmware commit, publish actual `.uf2` and its own `SHA256SUMS.txt`; confirm GitHub API lists real asset names, byte counts and the final UF2 `digest`. The candidate firmware hash may differ from the published rebuilt artifact. Record release notes and known terminal OS/application-specific HID shortcut behavior.
3. **Review simulator source drift.** Compare the newly released firmware's UX rows/dynamic masks, HAT controls, menus, colors, keyboard/media IDs and BLE profile semantics against `assets/js/screens.js`, renderer, HAT interaction, projector, virtual mice and independent `tests/fixtures/firmware-screens-v*.js`/LCD goldens. Adapt website code only if the physical firmware differs. Do not blindly copy features or promise hardware parity based solely on UI graphics.
4. **Keep test data isolated.** Run browser-only `/tests/` without touching the production simulator's locally saved virtual mice. Verify on real desktop/mobile browsers, keyboard/touch, HiDPI/zoom, sticky HAT, pairing/removal, profiles, Modifier/Movement, Help/Lock and optional diagnostics. Preserve the accepted removal of obsolete brightness/density controls.
5. **Deploy and confirm Pages.** Publish reviewed website changes, check GitHub Pages run for the exact commit, then test actual public `https://remappingbridge.github.io/` and `/tests/` in a real browser. A green deploy alone is not proof of runtime behavior.
6. **Update firmware README LAST.** The first screen retains **OPEN LIVE SIMULATOR**, direct verified UF2 and two credited Pico/LCD photos. In the installation section and top CTA, update tag, **exact versioned UF2 filename**, release note reference, byte count, SHA-256, `SHA256SUMS.txt` link. Keep stable `/releases/latest`. Never use a fictional automatically changing `latest/download/<versioned name>` link.
7. **Maintain navigation and originality.** Whenever top-level README headings change, update **Table of contents directly before Why use it?** and verify GitHub-generated slugs. Audit all relative paths, alt text, real board SKU, correct Pico 2 W / RP2350 vs 40-pin HAT labels, original SVGs and external photo attribution. **Do not reintroduce the operator-rejected “Curious?” paragraph or large static simulator preview unless the operator explicitly requests it.**
8. **Preserve safe-update boundaries.** BOOTSEL uses Micro-USB data, no routine `flash_nuke`/mass erase, no universally guaranteed BLE bond migration or old v2 schema round-trip. Shortcuts are host/application-dependent, the simulator is browser-only, and LCD Lock is not an input lock.
9. **Record real acceptance.** Maintain per-gate preflight, PR/commit SHA, automation/static checks, manual/browser/physical checks separately, operator corrections/acceptance decision, open risks and rollback path; do not promote “published”, “CI green” or “Pages deployed” to “operator accepted”.

10. **Public docs stay public-friendly.** Do not publish gate numbers, operator acceptance, development chronology, automated-test histories, git hashes, developer-only GPIO source mappings or internal release-maintainer chores in public READMEs. Keep those technical records here in the planner. README users need brief benefits, accurate usage, compatibility, complete safe installation, clear downloads, license and support.
